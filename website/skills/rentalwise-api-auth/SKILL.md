# RentalWise API: authentication and client setup

RentalWise is a property management system (PMS) for vacation rentals. A standalone website built
on it uses the REST API for three things only: reading data (properties, collections, locations,
amenities, availability, prices), creating bookings, and taking payments. Site configuration
(which currencies and languages to offer, branding, navigation, page content) lives in the website
project, not in RentalWise; the languages the content exists in come from `language/query`
(`rentalwise-languages-and-translations`). This skill sets up the connection; the other skills in
the set (`rentalwise-search-properties`, `rentalwise-property-details`,
`rentalwise-quote`, `rentalwise-booking`, `rentalwise-payment-page`, `rentalwise-languages-and-translations`) assume the client
described here exists.

## 1. What you need from the customer

| Setting | Example | Where it comes from |
|---|---|---|
| Base URL | `https://app.rentalwise.io/rest/` (production), `https://demo.rentalwise.io/rest/` (demo) | The RentalWise instance the customer's account lives on. Always ends in `/rest/`. |
| API token | a long opaque string | Generated by the customer in their RentalWise account (API keys are issued on ota.rentalwise.io for website/OTA integrations). A bearer token with no expiry you have to manage. |

That is all. There is no site id, channel or domain to register; the website identifies itself
through `source_name` on the bookings it creates. Put the two values in environment variables
and never hard-code them:

```bash
RENTALWISE_BASE_URL=https://app.rentalwise.io/rest/
RENTALWISE_API_TOKEN=...
```

## 2. The token stays on the server (non-negotiable)

The token grants broad access to the customer's PMS account. Anyone who reads it can list every
booking, guest and payment of that customer, so the browser must never see it. There is no
public or "publishable" key for this API and no CORS mode that makes a browser call acceptable.
Build the site so that every RentalWise call runs in server code:

- Server-rendered pages, static generation, API routes, route handlers, serverless and edge
  functions call the API directly. Browser code never holds the token and never calls a
  `*.rentalwise.io` URL.
- Interactive features (search, quote, booking form, calendar, destination type-ahead) go through
  thin backend routes the browser calls, for example `POST /api/property/search` or
  `POST /api/quote`. The route validates the body, forwards it to RentalWise with the token and
  returns only the fields the page needs.
- Backend routes expose specific calls. Do not create a generic proxy that forwards arbitrary
  resource/action paths or raw `where` bodies, because the same token can read bookings and
  guest data.
- A static site or single-page app with no server (plain Vite/React, static Astro output, a
  CDN-only deploy) needs one before it can use RentalWise: serverless functions (Vercel, Netlify,
  Cloudflare, AWS Lambda) or a small Node service. Never call the API from the browser, not even
  as a temporary shortcut.
- Environment variables with a public prefix are compiled into the browser bundle. Never name the
  token `NEXT_PUBLIC_*`, `VITE_*`, `REACT_APP_*`, `PUBLIC_*`, `NUXT_PUBLIC_*`, `EXPO_PUBLIC_*`,
  `GATSBY_*` or any other framework-public prefix, and never read it through `import.meta.env`
  in code the browser can import. Keep `.env*` files out of version control.
- Keep the client module where the framework refuses to bundle it for the browser (Next.js:
  `import 'server-only'` at the top of the file; other stacks: a `server/` folder that client
  code never imports) and keep the runtime guard the client asset ships with.
- Never put the token in a URL, a cookie, a log line, or an error payload returned to the
  browser. Never forward the upstream request (its `Authorization` header) or the raw upstream
  response headers.

## 3. Making requests

Every endpoint is `POST {BASE_URL}{resource}/{action}` with a JSON body, even reads. Headers:

```
Authorization: Bearer <RENTALWISE_API_TOKEN>
Content-Type: application/json
Accept: application/json
```

Resources and actions are kebab-case (`property/get-quote`, `property/get-unavailability`).
Read `references/request-conventions.md` for the response envelope, pagination, the `where` /
`with` / `sort` query language, the error formats and the map of every endpoint this skill set
uses.

Use plain HTTP. `@onemineral/pms-js-sdk` is deprecated: do not add it to new projects, and
replace it when you meet it in an existing one (`pms.property.search(params)` is just
`POST property/search` with the same body; the SDK wrapped the payload in `{ response }`, the
raw API does not).

`assets/rentalwise-client.ts` is a dependency-free fetch wrapper: copy it into the project's
server-only folder. It throws if loaded in a browser, throws a `RentalWiseError` with
`statusCode`, `responseBody` and flattened `messages` on non-2xx responses, and returns the JSON
payload as-is. An optional third argument adds request headers, e.g.
`rw.post(path, body, { headers: { 'x-locale': 'fr' } })` for translated validation messages.

```ts
// lib/server/rentalwise.ts  (Next.js: add `import 'server-only';` as the first line so a client
// component that imports this file fails the build instead of shipping the token)
import { createRentalWiseClient } from './rentalwise-client';

export const rw = createRentalWiseClient({
    baseURL: process.env.RENTALWISE_BASE_URL!,
    token: process.env.RENTALWISE_API_TOKEN!,
});

const page = await rw.post('property/search', { website_visible: true, guests: 2 });
```

In any other language the same four lines of HTTP do the job. The equivalent curl:

```bash
curl -sS -X POST "$RENTALWISE_BASE_URL/property/query" \
  -H "Authorization: Bearer $RENTALWISE_API_TOKEN" \
  -H "Content-Type: application/json" -H "Accept: application/json" \
  -d '{"paginate":{"page":1,"perpage":1},"where":{"conditions":[{"field":"status","in":["enabled"]}]}}'
```

## 4. The API documents itself: `settings/fetch`

`POST settings/fetch` with `{}` returns, under `schema`, a description of every resource: its
actions, each action's arguments with type, required/nullable flags, defaults and picklist
values, the `response_type`, and the fields of each record type with their relations. This is
the authoritative reference; the tables in this skill set were generated from it. When a
parameter is in doubt, or a newer PMS release may have changed something, read the schema
instead of guessing:

```bash
scripts/schema.py args property/get-quote      # arguments of one endpoint
scripts/schema.py fields booking               # fields of a record type (what `with` can load)
scripts/schema.py actions property             # every action of a resource and what it returns
scripts/schema.py find coupon                  # search names across the whole schema
```

**Download the schema once, then answer every question from the file on disk.** The first run
in a project (`scripts/schema.py --refresh resources`, with `RENTALWISE_BASE_URL` and
`RENTALWISE_API_TOKEN` set) saves the `schema` key, about 2 MB, as `.rentalwise-schema.json` at
the project root (the nearest directory with `.git`, `package.json` or `composer.json`; override
with `RENTALWISE_SCHEMA_CACHE`). Every later `schema.py` command reads that file: no network, no
token, and it finds the file from any subdirectory. Whenever you wonder which arguments an
action takes, what a field's type is, which relations `with` accepts or whether an action exists,
run the script against the cache; do not call `settings/fetch` again and do not re-download
because you changed directory. `scripts/schema.py status` prints where the cache is, how old it
is and how many resources it holds. Refresh only when the PMS was upgraded or when the script
reports as unknown something a newer reference claims exists.

Do not read `.rentalwise-schema.json` into the conversation: it is far too large. Query it with
the script, or with `jq` for an ad-hoc question:

```bash
jq '.property.actions["get-quote"].args | keys' .rentalwise-schema.json
jq '.booking.fields | to_entries[] | select(.value.type | test("has-|belongs-")) | .key' .rentalwise-schema.json
```

Without Python, create the same cache once with curl and keep working from it:

```bash
curl -sS -X POST "$RENTALWISE_BASE_URL/settings/fetch" -H "Authorization: Bearer $RENTALWISE_API_TOKEN" \
  -H "Content-Type: application/json" -H "Accept: application/json" -d '{}' | jq '.schema' > .rentalwise-schema.json
```

Add `.rentalwise-schema.json` to `.gitignore`. The rest of the `settings/fetch` response
describes the account (tenant, profile, subscription) and is of no use to a website, except
`tenant.settings.timezone` (the account's display timezone). The schema is a development-time
tool: never fetch it from application code or per request.

How to read it:

- `schema[resource].actions[action].args` is the request body. A `composed` argument is a
  nested object (`fields` lists its keys); `list-of` is an array of the inner type; `id` is an
  integer record id; `daterange` is `{ start, end }`; `translated-text` is a map keyed by the account's language codes
  (`rentalwise-languages-and-translations`);
  `picklist` lists `possible_values`.
- `schema[resource].fields` is the record you get back. Relation types (`belongs-to`,
  `has-many`, `has-one`, `belongs-to-many`) name the related resource in `relates_to`; those are
  the names you can put in `with`, dotted for nesting (`rooms.beds.bed_type`).
- `response_type` names the resource whose `fields` describe the response. `query` and `search`
  wrap it in the paginated envelope; `data` means a bare `{ data: ... }` JSON object.
- The schema describes what an argument accepts, not what the server does with it on every
  code path. `property/search` accepts `paginate` and currently ignores it (see the search
  skill). When a behaviour matters, make one real request and look.

## 5. Verify the credentials before building anything

Run `scripts/smoke-test.sh` (needs `RENTALWISE_BASE_URL` and `RENTALWISE_API_TOKEN` in the
environment). It prints how many enabled, website-visible properties the token can see. A 401
means the token or base URL is wrong; fix that before writing application code, because every
later error would be misleading. Zero visible properties means the customer has not marked any
property as website-visible yet; ask them before debugging the search.

## 6. Endpoints a website may call

Stay inside this list. The token can reach the whole PMS (bookings of other guests, owner
statements, settings), but a standalone website only reads catalogue data and creates bookings
and payments:

| Read | Write |
|---|---|
| `property/search`, `property/query`, `property/fetch`, `property/get-unavailability`, `property/get-occupancy-rates`, `property/get-applicable-discounts`, `property/get-quote` | `property/create-booking` |
| `service/query-available`, `service/price-services`, `service/price-services-for-booking`, `service/price-for-booking` (extras / upsells; newer PMS releases only, see `rentalwise-booking`) | `booking/add-services` (extras added to the guest's own booking before payment) |
| `collection/query`, `collection/fetch`, `location/query`, `amenity/query`, `amenity-group/query`, `property-type/query`, `tag/query`, `currency/query`, `country/query`, `language/query`, `settings/fetch` (schema, development time only) | `payment/create-client-secret` |
| `booking/fetch` / `booking/query` for the guest's own booking only, `payment-method/query` | `inquiry/create` (contact forms, optional) |

Everything else (`*/create`, `*/update`, `*/delete` on properties, guests, bookings, settings, or
any endpoint that is not listed) is back-office territory; a website has no reason to call it.

## 7. Error handling rules

| Status | Meaning | What to do |
|---|---|---|
| 401 | bad or missing token | Fail loudly in logs, never retry in a loop, never fall back to another token. |
| 422 | validation failed | `responseBody.errors` is a map of field or rule name to an array of messages, plus a top-level `message` (either "The given data was invalid." or the first error message). Show the messages to the user for forms; treat quote rule keys as "not available" (quote skill). |
| 500 with `exception_type: "response_exception"` | a business rule, not a crash | Read `message`; e.g. `get-occupancy-rates` on a daily-priced property. Handle like a 422. |
| 500 with `Action with name "x" is not registered` | wrong path | Fix the resource/action name (kebab-case). The API does not answer 404 for this. |
| other 5xx / network | upstream problem | Return a generic error to the browser, log the request path, status and response body. |

Log the URL, status, request payload and response body on failure. Do not log the token or the
request headers. The browser receives a generic message plus, for 422, the validation messages;
it never receives the upstream body of a 401 or 5xx.

## 8. What may go to the browser

| Send to the browser | Keep on the server |
|---|---|
| Search results, property content, collection and location records, reference data | `RENTALWISE_API_TOKEN`, `RENTALWISE_BASE_URL`, any `Authorization` header |
| The quote breakdown and `quote_id`; the service catalogue for the stay and the priced service lines with `services_quote_id` | Property `geo` (exact position), `access_pin_code`, `checkin_instructions` / `checkout_instructions` and their PDF links |
| The guest's own booking, trimmed for the payment page (dates, amounts due, price lines; see `rentalwise-payment-page`), through a URL that does not expose the booking id | Any other booking, guest or payment record; `booking/query` results that are not filtered to the guest's id and identifier |
| The payment widget `client_secret` and `instance` | The `payment/create-client-secret` call itself |

When a backend route returns an API record, map it to the fields the page renders instead of
passing the record through. A property record has close to a hundred fields, several of them
operational (`access_pin_code`, `ical_url`, health scores), and new ones arrive with PMS
releases without being reviewed for exposure.

## 9. Caching and rate limits

The API is not designed to be hit on every page view by every visitor. Cache reference data
(locations, amenities, currencies) and property content for an hour or more, and revalidate in
the background. Never cache quotes, availability or bookings beyond the request that produced
them: prices and availability change at any time.

## Checklist before moving on

- [ ] `RENTALWISE_BASE_URL` ends with `/rest/` and `RENTALWISE_API_TOKEN` is set server-side only,
      with no public prefix (`NEXT_PUBLIC_`, `VITE_`, `REACT_APP_`, `PUBLIC_`, ...)
- [ ] `scripts/smoke-test.sh` succeeded
- [ ] A single shared client module exists (`assets/rentalwise-client.ts` or an equivalent
      plain-HTTP wrapper, no SDK), is marked server-only and is imported only by server code
      (pages' data loaders, API routes, functions)
- [ ] `.rentalwise-schema.json` exists at the project root (one `scripts/schema.py --refresh`
      run) and is git-ignored; every later schema question was answered from that file with
      `schema.py` or `jq`, never by calling `settings/fetch` again; parameter names in the
      code match `schema.py args <resource>/<action>`
- [ ] Browser-facing routes forward only the specific calls the pages need and return mapped
      fields, not raw records
- [ ] `grep -rn "rentalwise.io/rest\|RENTALWISE_API_TOKEN\|Bearer " <client source dirs>` finds
      nothing, and after a production build
      `grep -rl "$RENTALWISE_API_TOKEN" .next/static dist build public 2>/dev/null` prints nothing
